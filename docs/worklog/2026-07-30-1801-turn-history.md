# Canonical Turn Records and Move History

Timestamp: 2026-07-30-1801

Previous worklog: docs/worklog/2026-07-30-1752-staged-move-ux.md

Goal:

Add an immutable, canonical completed-turn record model and in-memory turn history UI with explicit historical inspection mode, while preserving existing engine legality, staged prefix behavior, and opening-roll orchestration boundaries.

Canonical record shape:

- Added engine-exported turn record model:
  - `TurnRecord`
  - `TurnOutcome`
  - `TurnPhase`
  - `CreateTurnRecordInput`
- Record fields capture:
  - sequential turn number
  - acting player
  - exact turn dice
  - explicit move/pass outcome
  - committed position before
  - committed position after
  - game status after
  - opening/normal phase

Type placement decision:

- Placed canonical turn-record types and immutable constructor in `packages/backgammon-engine`.
- Rationale:
  - data model is deterministic game-domain output, not presentation state
  - references engine move/dice/status semantics directly
  - remains reusable by web/server/worker/native layers without React coupling
  - avoids creating a speculative new package for one focused model

Portability rationale:

- Record model has no dependency on React, DOM, CSS, browser storage, or UI component contracts.
- Values are immutable snapshots and can be serialized/replayed later by any host runtime.

Record immutability expectations:

- Added `createTurnRecord(...)` helper in engine package to deep-clone:
  - dice
  - move outcome payload
  - before/after positions
  - game status payload
- App history always appends freshly created immutable snapshots.
- Failed transitions and staged interactions never append history.

When records are created:

- Records are appended only after successful committed transitions:
  - successful `applyGameMove(...)`
  - successful `passTurn(...)`
- No record is created for:
  - opening-roll ties
  - staged prefix selection
  - undo staged step
  - failed move/pass attempts

Move versus pass representation:

- Move records store canonical complete `Move` accepted by move application flow.
- Pass records store explicit `{ kind: "pass" }` outcome.
- No fake empty move representation is used for passes.

Opening-turn representation:

- Opening turn is recorded as ordinary turn record with `phase: "opening"`.
- Opening roll ties remain UI-only pre-turn state and do not create records.

Turn-number convention:

- Sequential numbering starts at 1.
- Each successful committed turn increments by exactly one.
- New Game clears history and the next committed turn restarts at 1.

History-state ownership:

- Web app owns in-memory `turnHistory` and current `historyInspection` state.
- Record construction is centralized through one append helper path in `App.tsx`.
- Engine remains the authority for legality and position transitions.

Historical board inspection behavior:

- Added `TurnHistoryPanel` with:
  - readable turn list (`turn number`, `player`, `phase`, `dice`, `move/pass`)
  - selected-turn details (`player`, `dice`, `outcome`, step metadata, before/after summaries)
  - navigation controls (`View Before`, `View After`, `Previous Turn`, `Next Turn`)
  - `Return to Current Game`
- Main board is reused for inspection display; before/after record positions are shown explicitly.

Live game versus history mode behavior:

- While inspection is active:
  - checker selection/hover interaction disabled
  - staged projection and candidate preview usage disabled
  - opening-roll, roll dice, pass, and manual dice controls disabled
  - New Game remains available
- Returning exits inspection and restores the live committed board/state context.

Staged-selection policy when inspection begins:

- Policy chosen: clear staged selection when entering history inspection.
- Committed game state is not mutated by this clear.

New Game reset behavior:

- New Game now resets:
  - committed game state
  - opening-roll state and opening-turn pending
  - manual dice selectors
  - staged selection/source/hover/message
  - complete turn history
  - active history inspection mode

Engine API impact:

- Added public turn-record type exports and `createTurnRecord(...)` helper.
- No changes to legal move generation, prefix projection rules, move equivalence, or transition semantics.

Move-legality impact:

- None.
- `getLegalMoves(...)`, `applyMove(...)`, `applyGameMove(...)`, `passTurn(...)`, and `previewMovePrefix(...)` behavior remains unchanged.

Notes for future contributors:

- Keep durable turn-record data in engine-domain types; avoid embedding canonical record shape in React-only modules.
- Continue appending records only on successful committed transitions.
- Keep staged interaction state transient and separate from committed history.
- Keep history persistence/export out of scope until a dedicated persistence milestone.
