# Evidence Selection and Knowledge Retrieval

## Purpose

This milestone improves what the coach sees before the model answers.

- deterministic game and position facts still come from engine and analysis layers
- evaluator-attributed move ranking still keeps explicit provenance
- curated knowledge now supplies a small amount of project-authored instructional guidance
- the coach now receives selected legal move evidence instead of a broad undifferentiated move dump

The board remains the workspace and typed conversation remains the primary interface.

## Authority boundaries

Three information categories are kept distinct in both data and prompt construction:

1. Deterministic facts
2. Evaluator-attributed position-specific evidence
3. Curated general guidance

Deterministic facts remain authoritative for board state, legal moves, committed history, and factual position deltas.

Evaluator evidence may contribute rank, normalized score, loss from best, provenance, and coverage when available.

Historical review evidence now additionally records:

- committed-turn review target source (explicit selection vs latest committed fallback)
- canonical played move and whether it was evaluator-covered
- strongest evaluated alternative when available
- explicit limitations for partial, uncovered, fixture, unavailable, or failed evaluation

Current-position evidence now also includes recommendation-support resolution before model generation:

- supported authoritative recommendation (complete trustworthy evaluator coverage)
- supported strongest-evaluated recommendation (partial evaluator coverage)
- not-supported recommendation (fixture evaluator, missing evaluator, non-decision, or no-legal-move)

History-turn evidence uses parallel support states and adds:

- `played-move-not-evaluated` when the played move is legal but uncovered
- `unsupported-history-turn` for non-checker historical actions

Curated knowledge may explain general ideas such as hitting, point making, bar entry, or race-versus-contact. It is not authoritative for what is true in the current position.

## Package placement

The retrieval boundary remains in `@backgammon-trainer/backgammon-coach`.

Curated content lives in `@backgammon-trainer/backgammon-knowledge`.

Why this split is durable:

- the coach layer decides which factual context and retrieval concepts matter for a question
- the knowledge layer owns authored content, taxonomy, validation, and browser-safe retrieval helpers
- a future semantic or hybrid retriever can replace the current local matcher without changing coach orchestration, prompt construction, or web UI behavior

## Curated knowledge source

Canonical authored knowledge lives as markdown under `packages/backgammon-knowledge/content/`.

Browser delivery uses a checked-in generated TypeScript corpus at `packages/backgammon-knowledge/src/generated/corpus.ts`.

The markdown source is canonical. Generated TypeScript is only the browser-safe delivery artifact.

Validation detects stale generated output so browser code never needs filesystem access.

## Knowledge taxonomy

The taxonomy is authoritative inside `@backgammon-trainer/backgammon-knowledge`.

Current tracks:

- `board-vision`
- `safety-risk`
- `making-points`
- `hitting-tempo`
- `game-plan-recognition`
- `move-review`

Current concept set is controlled and intentionally bounded. It supports retrieval and corpus review rather than rules logic.

New entries should use the smallest concept set that honestly matches the content.

## Legal move references in questions

The coach layer recognizes move-like question text such as:

- `13/8`
- `13-8`
- `13 to 8`
- `13/8, 6/4`

Resolution is always constrained to legal candidates already generated by the engine-derived move-outcome analysis.

Supported outcomes:

- `clear`: one legal candidate matches the referenced full move
- `partial`: the reference matches one or more legal candidates as a subset of steps
- `ambiguous`: the reference matches multiple full legal candidates
- `unmatched`: the text looks move-like but matches no legal candidate

The coach layer never constructs or applies a move from user prose.

## Evidence selection behavior

For current-position questions, the coach does not send every legal move row by default.

Instead it deterministically selects a bounded subset based on:

1. legal moves clearly or partially referenced in the question
2. currently staged candidate moves from the UI
3. ranked comparison candidates when evaluator results are present
4. factually distinct alternatives such as hits, point-making changes, or bearing-off changes
5. deterministic fallback when no stronger signal exists

Each selected row records explicit selection reasons.

The public coach evidence bundle version is now `2` to reflect the added selection, coverage, and retrieval semantics.

Each request also records:

- total legal move count
- selected legal move count
- omitted legal move count
- coach evidence coverage (`complete` or `selected-subset`)
- question move-reference resolution details
- truncation warnings when bounded selection discards additional relevant rows

Legal move coverage, evaluator coverage, and coach evidence coverage remain separate concepts.

## Factual retrieval concepts

The coach layer derives neutral retrieval concepts from trusted evidence only.

Current examples include:

- `current-position`
- `candidate-comparison`
- `hits`
- `blots`
- `bar-entry`
- `bearing-off`
- `made-points`
- `contact`
- `race`
- `inner-board`
- `move-review`

These concepts describe what is factually present. They do not express strategic verdicts.

## Retrieval behavior

The local retriever is deterministic, bounded, inspectable, and provider-neutral.

Inputs:

- user question text
- resolved context kind
- factual retrieval concepts derived by the coach layer
- `maxItems`

Selection rules:

- alias matches and concept matches are stronger than context-only overlap
- generic context-only matches are ignored to avoid filler results
- no-match is valid
- tie-breaking is deterministic by score, reason count, then stable entry id

Returned entries keep:

- stable identity
- title and summary
- educational body text
- track and concepts
- project-authored provenance
- explicit retrieval reasons

## Prompt integration

`buildCoachModelRequest(...)` now sends a compact structured envelope with:

- the user question
- response preferences
- context kind
- deterministic evidence
- curated knowledge
- truncation metadata

Developer instructions explicitly tell the model that:

- deterministic evidence is authoritative for board facts and legal moves
- evaluator evidence retains provenance and may be partial
- curated knowledge is general guidance only
- omitted move rows may still be legal
- insufficient evidence must be acknowledged rather than invented
- evaluator ranking authority comes from supplied recommendation-support state, not model inference

## Fixture model behavior

The fixture chat model remains non-strategic.

It may summarize:

- context kind
- selected move evidence count versus total legal moves
- curated knowledge count and a few titles
- warning count

It does not recommend moves or pretend to be expert advice.

## Web transparency

The Coach panel remains conversation-first.

The disclosure beneath responses now surfaces compact inspection details for:

- selected versus total legal move evidence
- omitted move counts
- question move-reference handling
- evaluator provenance and coverage
- curated knowledge identities and retrieval reasons
- bounded warnings

The UI does not render the raw knowledge corpus, raw markdown, or unsafe HTML.

## Failure behavior

Retrieval is advisory.

- retrieval failure does not block a coach request
- unmatched or ambiguous move references become warnings, not fabricated moves
- no-match knowledge retrieval is valid
- gameplay remains enabled during coach work
- stale prior-lineage responses are still ignored

If evidence selection fails to find a strong current-position subset, deterministic fallback still uses trustworthy legal candidates.

## Persistence boundary

This milestone does not persist:

- conversations
- request snapshots
- move-reference matches
- selected evidence rows
- retrieved knowledge entries
- coach responses

Curated knowledge is repository source content, not user persistence.

## Extension points

Future milestones may replace the current local matcher with:

- semantic retrieval
- embeddings
- vector or hybrid indices
- remote retrieval behind a provider-neutral boundary

The following remain stable when that happens:

- coach orchestration
- evidence construction
- prompt integration
- web conversation experience
- disclosure semantics
- persistence exclusions

## Current limits

- local lexical retrieval only
- beginner-oriented initial corpus only
- no strategic verdict generation
- no long-term habit analysis
- no semantic ranking
- real provider support is currently one server-hosted OpenAI-compatible non-streaming text adapter only
- real GNU evaluator server mode is available through the provider-neutral server evaluator boundary
